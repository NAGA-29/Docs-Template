# ストレステスト・負荷試験 計画／実施テンプレート

> 対象: Web API、Webアプリケーション、バックエンドサービス、バッチ、キュー処理、DB書き込み処理など  
> 目的: 性能限界、劣化開始点、障害時の挙動、復旧性を確認する  
> 想定読者: 負荷試験の初心者〜実務担当者

---

## 0. このテンプレートの使い方

このテンプレートは、負荷試験を以下の順番で進めるための確認表です。

1. 試験の目的を決める
2. 合格条件を決める
3. 本番に近い試験環境を用意する
4. 負荷パターンを作る
5. アプリ・OS・DB・外部サービスの指標を収集する
6. 段階的に負荷を上げる
7. 限界値と原因を特定する
8. 改善後に再試験する

「サーバーが落ちるまでアクセスする」だけでは不十分です。  
実務では、サーバーが落ちる前に発生するレイテンシ悪化、エラー増加、DB接続枯渇、キュー滞留、データ欠損などを見つけることが重要です。

# 16. 初心者向け用語集

## RPS

Requests Per Secondの略。  
1秒間に何件のリクエストを処理したかを表す。

```text
1秒間に500件送信 = 500 RPS
```

## TPS

Transactions Per Secondの略。  
1秒間に完了した業務処理数。RPSと同じ意味で使われる場合もあるが、1トランザクション内で複数リクエストを行う場合は異なる。

## VU

Virtual Userの略。  
k6などの負荷試験ツール上で動く仮想ユーザー。

VUが100でも、各VUがゆっくりアクセスするならRPSは低い。  
そのため、VU数だけでは負荷量を判断できない。

## レイテンシ

リクエストを送信してからレスポンスを受け取るまでの時間。

```text
200ms = 0.2秒
1,000ms = 1秒
```

## 平均レイテンシ

すべての応答時間の平均。  
一部の非常に遅いリクエストが埋もれるため、平均値だけで判断してはいけない。

## p50

全リクエストの50%が、この時間以内に完了したことを示す。中央値とも呼ばれる。

## p95

全リクエストの95%が、この時間以内に完了したことを示す。

```text
p95 = 300ms
→ 95%は300ms以内
→ 残り5%は300msより遅い
```

## p99

全リクエストの99%が、この時間以内に完了したことを示す。  
一部ユーザーだけが大きく待たされる問題を見つけやすい。

## スループット

単位時間あたりに処理できる量。  
APIならRPS、Queueならmessages/sec、DBならqueries/secなどで表す。

## エラー率

全リクエストのうち失敗した割合。

```text
10,000件中10件失敗
エラー率 = 0.1%
```

## Timeout

指定した時間内に処理が終わらず、呼び出し側が失敗と判断すること。

## SLI

Service Level Indicatorの略。  
サービス品質を表す実測値。

例:

- p95レイテンシ
- 成功率
- エラー率
- 稼働率
- データ反映時間

## SLO

Service Level Objectiveの略。  
サービス品質の目標値。

例:

```text
p95レイテンシを300ms未満にする
成功率を99.9%以上にする
```

SLOは「どこまでなら正常と判断するか」という合格基準。

## SLA

Service Level Agreementの略。  
顧客との契約として保証するサービス水準。  
SLOは内部目標、SLAは対外的な契約と考えると分かりやすい。

## Baseline Test

低負荷で基準値を取る試験。  
最初に実施し、通常時のCPU、メモリ、レイテンシを記録する。

## Load Test

想定する通常負荷やピーク負荷をかけ、問題なく処理できるか確認する試験。

## Stress Test

負荷を段階的に増やし、性能劣化や限界を確認する試験。

## Spike Test

短時間で急激にアクセスを増やす試験。  
一斉ログイン、ネットワーク復旧、イベント開始直後などを再現する。

## Soak Test

数時間〜数日間、一定負荷を継続する試験。  
メモリリーク、接続リーク、徐々に進む性能低下を見つける。

## Endurance Test

Soak Testとほぼ同じ意味。長時間耐久試験。

## Scalability Test

サーバー数やCPUを増やしたとき、処理能力がどれだけ増えるか確認する試験。

## Breakpoint

システムが正常動作できなくなる境界。  
ただし、完全停止する点だけでなく、SLOを守れなくなる点も重要。

## Saturation

CPU、メモリ、DB接続、Network、Diskなどの資源が使い切られた状態。

## Bottleneck

全体性能を制限している箇所。

例:

- APIサーバーのCPU
- DBのconnection数
- RedisのNetwork
- Queue Workerの処理速度
- 外部APIのレート制限

## Ramp-up

負荷を少しずつ増やすこと。

```text
100 RPS
→ 300 RPS
→ 500 RPS
→ 1,000 RPS
```

突然最大負荷をかけるより、劣化開始点を特定しやすい。

## Ramp-down

負荷を少しずつ減らすこと。  
負荷低下後に正常状態へ戻るか確認する。

## Throughput Collapse

負荷を増やしたのに、処理成功量が逆に減少する現象。  
Retryの増加、ロック競合、GC、DB接続待ちなどで起こる。

## Backpressure

後続処理が遅いとき、入口側で受け付け量を制御する仕組み。  
無制限に受け付けてメモリやQueueを溢れさせないために使う。

## Rate Limit

一定時間内に受け付けるリクエスト数を制限する仕組み。

## Queue Depth

Queueに溜まっているメッセージ数。

## Oldest Message Age

Queue内で最も古いメッセージが、何秒待っているかを表す。  
Queue Depthよりも、実際の遅延を判断しやすい場合がある。

## Retry

失敗した処理を再実行すること。  
Retryが多すぎると、障害中のシステムへさらに負荷をかける。

## Retry Storm

多数のクライアントやサービスが同時にRetryし、障害を悪化させる現象。

## Exponential Backoff

Retry間隔を徐々に長くする方式。

```text
1秒後
2秒後
4秒後
8秒後
```

## Jitter

Retry時刻が集中しないように、待機時間へランダムなズレを加えること。

## Circuit Breaker

外部サービスが失敗し続ける場合、一時的に呼び出しを止める仕組み。  
障害中のサービスへ無限にアクセスし続けることを防ぐ。

## Connection Pool

DBや外部サービスとの接続を使い回す仕組み。  
接続数が少なすぎると待ちが発生し、多すぎるとDB側を圧迫する。

## Connection Pool Exhaustion

接続プールを使い切り、新しい処理が接続待ちになる状態。

## File Descriptor

OSがSocketやファイルを管理するための番号。  
大量接続で上限に達すると、新しい接続を受け付けられなくなる。

## OOM

Out Of Memoryの略。  
メモリ不足。OSやコンテナによってプロセスが停止されることがある。

## OOM Kill

メモリ不足によって、OSやコンテナ基盤がプロセスを強制終了すること。

## GC

Garbage Collectionの略。  
不要なメモリを回収する処理。  
GCが頻発すると、CPU使用率やレイテンシが悪化する場合がある。

## Memory Leak

不要になったメモリが解放されず、使用量が増え続ける問題。

## Goroutine Leak / Thread Leak

終了するはずのgoroutineやthreadが残り続け、数が増える問題。

## CPU Throttling

コンテナや仮想環境で、設定されたCPU上限を超えたため処理が抑制されること。

## TTFB

Time To First Byteの略。  
リクエスト送信後、レスポンスの最初の1byteが返るまでの時間。  
サーバー処理待ち時間の目安になる。

## DNS Lookup Time

ドメイン名をIPアドレスへ変換する時間。

## TCP Connect Time

TCP接続を確立するまでの時間。

## TLS Handshake Time

HTTPS通信の暗号化接続を確立するまでの時間。

## Keep-Alive

HTTP接続を使い回す仕組み。  
無効だと毎回TCP/TLS接続が発生し、負荷が増える。

## Dropped Iterations

k6が予定していたリクエストを生成できなかった数。  
対象サーバーではなく、k6側が限界になっている可能性がある。

## Warm Cache

必要なデータがRedisやメモリ、DBキャッシュに読み込まれている状態。

## Cold Cache

キャッシュが空で、DBやStorageから読み込む必要がある状態。

## Slow Query

通常より長時間かかるDBクエリ。

## Lock Wait

他の処理が保持しているDBロックが解除されるまで待っている状態。

## Deadlock

複数処理が互いのロック解除を待ち続ける状態。  
DBが一方を強制的に失敗させて解消することが多い。

## Replication Lag

Primary DBの更新がReplicaへ反映されるまでの遅延。

## Data Loss

送信されたデータが保存されないこと。  
HTTP 200でも後続処理に失敗していれば発生する。

## Duplicate Processing

同じデータを複数回処理・保存してしまうこと。

## Idempotency

同じリクエストを複数回実行しても、結果が重複しない性質。

## Recovery Time

障害や過負荷が終了してから、正常状態へ戻るまでの時間。

## Headroom

現在の負荷から限界までの余裕。

```text
最大処理能力 1,000 RPS
現在 600 RPS
余裕 400 RPS
```

## Safety Margin

予測誤差や突発負荷に備え、最大能力ぎりぎりで運用しないための余裕。

例:

```text
SLOを守れる最大値 1,000 RPS
安全運用上限 600〜700 RPS
```

# 17. 初心者が陥りやすい失敗

- 平均レイテンシだけを見る
- HTTP 200なら成功と判断する
- k6側のCPUやNetwork上限を確認しない
- DBが空の状態だけで試す
- キャッシュが温まった状態だけで試す
- 負荷を一気に上げ、劣化開始点を特定できない
- サーバーが落ちたRPSだけを結果にする
- Queueの滞留を確認しない
- データ欠損や重複を確認しない
- 外部サービスのレート制限を無視する
- DEBUGログを大量に出したまま試験する
- 本番より小さいDBやサーバーで結果をそのまま換算する
- 一度だけ試験して結論を出す
- 改善後に同じ条件で再試験しない
- 負荷停止後の復旧を確認しない
