# 見積もり用 概算値チートシート（データ量・リクエスト・CPU）

Nov 24, 2026 · @naga

## 使い方（見積もりの流れ）

概算は「桁（オーダー）を合わせる」のが目的。2倍程度の誤差は気にせず、最後に安全率 ×2 を掛ける。

1. **規模を決める**：DAU と、1人1日あたりのリクエスト数
2. **平均RPS** = DAU × リクエスト数/人/日 ÷ 86,400（≒ 10万で割る）
3. **ピークRPS** = 平均RPS × 2〜5（業務系は営業時間に集中、イベント系は ×10 以上）
4. **必要vCPU** = ピークRPS × 1リクエストのCPU時間(秒) ÷ 目標CPU使用率（0.5〜0.7）
5. **帯域** = ピークRPS × レスポンスサイズ × 8（bit換算）
6. **ストレージ** = 1日の書き込み量 × 保持日数 × オーバーヘッド（インデックス等 ×2〜3）× 冗長化（レプリカ・バックアップ ×2〜3）

覚えておくと楽な近似：2¹⁰ ≒ 10³（1KiB ≒ 1KB）、1日 ≒ 10⁵ 秒、1Gbps ≒ 125MB/s。

### ピーク係数・同時接続

- 一般的なWeb/アプリ：平均の 2〜3倍
- 業務系（9〜18時に集中）：24時間平均の 3〜5倍
- イベント・チケット発売・プッシュ通知直後：10〜100倍
- ピーク同時接続ユーザー ≒ DAU × 5〜15%
- DAU/MAU は 0.1〜0.5 程度（毎日使うサービスほど高い）
- **リトルの法則**：同時処理中のリクエスト数 = RPS × 平均レスポンス時間（例：1,000 RPS × 0.2秒 = 200並列）。スレッド数・DB接続プール数の見積もりに使う

## 1台あたりの処理能力の目安

実装・ライブラリ・DB設計で数倍ぶれるので、あくまで初期見積もり用。最終的には負荷試験（k6、wrk など）で実測する。

### 1 vCPU あたりの RPS

| 処理内容 | RPS / vCPU | 1リクエストのCPU時間 |
| --- | --- | --- |
| 静的ファイル・キャッシュ返却（nginx） | 5,000〜20,000 | 0.05〜0.2 ms |
| Go / Rust：DBなしのシンプルなJSON API | 5,000〜20,000 | 0.05〜0.2 ms |
| Go：DBクエリ1〜3本のCRUD API | 500〜2,000 | 0.5〜2 ms |
| Node.js：DBありCRUD | 300〜1,000 | 1〜3 ms |
| Laravel（PHP-FPM）：DBありCRUD | 50〜200（Octaneで2〜5倍） | 5〜20 ms |
| Next.js SSR ページ生成 | 20〜100 | 10〜50 ms |
| 画像リサイズ・変換（1枚） | 5〜30 | 30〜200 ms |
| bcrypt（cost 10）でのログイン | 10〜20 | 50〜100 ms |

### 計算式

**必要vCPU = ピークRPS × CPU時間(秒) ÷ 目標使用率(0.6)**

例：ピーク1,000 RPS、CPU時間 5 ms → 1,000 × 0.005 ÷ 0.6 ≒ 8.3 → 8 vCPU（4 vCPU × 2台）

CPU時間はレスポンス時間とは別物。DBや外部APIの待ち時間はCPUを使わないので、APMやプロファイラ（Go なら pprof）で実測した値を使う。

### ストレージ

- 1日の書き込み量 × 保持日数 × 2〜3（インデックス等）× 2〜3（レプリカ・バックアップ）
- つまり生データの **3〜5倍** を見込んでおく
- ログは保持期間を決めてローテーション。1,000万リクエスト/日 × 500 B ≒ 5 GB/日

### 帯域

| 単位 | 換算 |
| --- | --- |
| 100 Mbps | 12.5 MB/s |
| 1 Gbps | 125 MB/s ≒ 450 GB/時 ≒ 10 TB/日 |
| 1 Mbps 常時 | 約324 GB/月 |

**ピーク帯域 = RPS × レスポンスサイズ × 8**

例：1,000 RPS × 50 KB = 50 MB/s = 400 Mbps

## 計算例

### 例1：業務SaaS（Go＋PostgreSQL）

前提：DAU 5万人、1人1日200リクエスト、9〜18時に集中、平均レスポンス 10 KB、2割が書き込み（1件 1 KB）

1. 1日のリクエスト：5万 × 200 = 1,000万
2. 営業時間9時間（32,400秒）で割る：約310 RPS → ピーク ×2 で **約600 RPS**
3. CPU：600 × 0.003秒（CPU時間 3 ms）÷ 0.6 ≒ **3 vCPU** → 冗長化して 2 vCPU × 2台
4. 帯域：600 × 10 KB = 6 MB/s ≒ **48 Mbps**
5. DB書き込み：200万件/日 × 1 KB = 2 GB/日 → 1年で約730 GB、インデックス込みで **約1.5〜2 TB** → パーティショニングやアーカイブを検討
6. ログ：1,000万 × 500 B = **5 GB/日**

### 例2：リアルタイムのモーション共有（WebSocket）

前提：同時接続 1,000人、10人1ルーム、60fps、1フレーム 0.7 KB

1. 上り：1人 0.7 KB × 60 = 42 KB/s → 全体 42 MB/s
2. 下り：ルームの他9〜10人分を配信 → 1人約420 KB/s → 全体 **約420 MB/s ≒ 3.4 Gbps**
3. メッセージ数：受信 6万 msg/s、配信（×10）60万 msg/s。Go で1コア 5〜10万 msg/s とすると **6〜12コア**
4. 削減策：float16 で量子化、30fps に落として補間、変化分だけ送る、P2P（WebRTC）に逃がす → 1/4〜1/8 にできれば 1 Gbps 以下・2〜3コアに収まる

このように、帯域とメッセージ数が先に限界に来るリアルタイム系は、CPUより先に通信量を見積もるのがコツ。
