| 項目       | 内容                                         |
| ---------- | -------------------------------------------- |
| 文書名     | 要件確認チェックリスト                       |
| バージョン | v1.0                                         |
| 位置づけ   | 要件定義・見積時の「聞き漏れ防止」ガイド     |
| 関連文書   | [要件定義書テンプレート](Requirements_Definition_Document_TEMPLATE.md) / [要求定義書テンプレート](Requirement_Analysis_Document_TAMPLATE.md) / [設計文書の使い分けガイド](design_documents_guide.md) |

> クライアント案件（受託）か自社開発かを問わず、要件定義・設計の初期に**確認すべき項目**と、**見積に必ず含めるべき項目**を整理したチェックリストである。  
> すべてを確定させる必要はない。重要なのは「**確認した結果、決まった / 決まっていない / 対象外**」を明示的に残すこと。

## 0. 使い方

### 0.1 進め方

1. 要件定義の着手時に、本書を**ヒアリングの質問リスト**として使う。
2. 各項目を `確定 / 仮置き / 未決 / 対象外(N/A)` のいずれかで判定する。
3. `仮置き` と `未決` は要件定義書の「未決事項」に転記し、**見積の前提**または**リスク**として明記する。
4. 確定した内容は要件定義書の該当章（機能要件 / 非機能要件 / スコープ）へ反映する。
5. 見積時は [第4章](#4-見積もるべき要件工数コストの見落とし防止) を使い、工数の抜け漏れを確認する。

### 0.2 判定の凡例

| 判定 | 意味 | 後続アクション |
| ---- | ---- | -------------- |
| 確定 | 数値・方式まで合意済み | 要件定義書に記載 |
| 仮置き | 暫定値で進める（根拠・見直し時期あり） | 見積前提に記載、確認期限を設定 |
| 未決 | 判断材料が不足 | 未決事項に登録（担当・期限） |
| N/A | 該当しない（理由を一言添える） | 対象外として記載 |

### 0.3 受託と自社開発の違い

確認する項目は同じだが、**「誰が決めるか」「誰が負担するか」** が異なる。

| 観点 | 受託（クライアント案件） | 自社開発 |
| ---- | ------------------------ | -------- |
| 要件の決定者 | クライアント（窓口と最終決裁者が別のことが多い） | 自社の事業責任者・PO |
| 曖昧な要件のリスク | 追加費用・納期・責任範囲の紛争になりやすい | 手戻り・スコープ膨張・優先順位の迷走になりやすい |
| 非機能要件 | 「お任せ」にされがち。**合意しないと瑕疵・不具合扱いになり得る** | 「後で考える」にされがち。**後から変更すると高コスト** |
| 見積 | 契約形態（請負/準委任）と一体で扱う | 工数・期間・ランニングコストを予算として確保 |
| 運用・保守 | 契約範囲外になりやすい（誰がやるのか曖昧） | 開発者がそのまま運用するため見落とされやすい |

## 1. プロジェクト前提の確認（スコープ・体制・契約）

要件の中身に入る前に、**プロジェクトの前提条件**を確認する。ここが曖昧だと以降の全要件がぶれる。

### 1.1 目的・スコープ

- [ ] なぜ作るのか（解決したい課題・達成したい状態）が一文で言えるか
- [ ] 成功指標（KPI・受け入れ基準）は何か。誰がどう測るか
- [ ] 対象範囲（やること）と**対象外（やらないこと）** が明文化されているか
- [ ] MVP / 初回リリース / 将来フェーズの区切りは決まっているか
- [ ] 優先順位（Must / Should / Could / Won't）は誰が決めるか
- [ ] 現行システム・現行業務は存在するか（置き換え / 併用 / 新規）
- [ ] 類似・競合・参考にするサービスはあるか（「◯◯のような」の具体的な範囲）

### 1.2 関係者・体制・意思決定

- [ ] 要件の最終決裁者は誰か（窓口担当者と決裁者が異なる場合はその両方）
- [ ] ステークホルダー一覧（利用部門・情報システム部門・法務・セキュリティ・経営層・外部ベンダー）
- [ ] 仕様確認の回答期限・レビューのリードタイム（例: 回答は3営業日以内）
- [ ] 定例会・連絡手段・議事録の承認フロー
- [ ] クライアント側の作業分担（データ準備・環境提供・テスト参加・承認）
- [ ] 開発体制（人数・スキル・稼働率・外部委託の有無）
- [ ] 既存システムの担当者・有識者に確認できるか（属人化・退職・ブラックボックスの有無）

### 1.3 契約・コスト・スケジュール

- [ ] 契約形態（請負 / 準委任 / SES / 自社内部予算）
- [ ] 予算上限・予算の性質（初期費用のみか、ランニングコスト込みか）
- [ ] 納期・マイルストーン（固定の外部要因: 法改正、イベント、決算、他システム更改）
- [ ] 納品物の一覧（ソース、設計書、テスト結果、操作マニュアル、運用手順書 等）
- [ ] 検収条件・検収期間・検収者
- [ ] 瑕疵担保 / 契約不適合責任の期間・範囲、無償保守期間
- [ ] 知的財産権（成果物・ソース・OSS利用）の帰属
- [ ] 再委託の可否、秘密保持・情報取扱いの条件
- [ ] 要件変更時のルール（変更要求の受付・見積・承認フロー）→ [`design/change/`](../change/README.md) を参照

### 1.4 制約・前提

- [ ] 指定技術・指定クラウド・指定ベンダーはあるか（社内標準、セキュリティ要件による固定）
- [ ] 既存システム・既存DB・既存API・既存認証基盤との接続要否
- [ ] 利用可能な環境（社内ネットワーク制限、プロキシ、閉域網、持ち込み機器の制限）
- [ ] 遵守すべき社内規程・ガイドライン（セキュリティポリシー、開発標準、命名規約）
- [ ] 準拠すべき法令・業界基準（[3.8 法令・コンプライアンス](#38-法令コンプライアンス) 参照）

## 2. 機能要件でよく確認すべき項目

業務固有の機能とは別に、**ほぼ全てのシステムで必要になるが、ヒアリングで抜けやすい機能**を整理する。  
「要望として出てこない = 不要」ではなく、**出てこなくても必要になる**ものが多い。

### 2.1 共通機能

| 分類 | 確認観点 | 見積への影響 |
| ---- | -------- | ------------ |
| 認証 | ID/パスワード、SSO（SAML/OIDC）、ソーシャルログイン、MFA、パスワードポリシー、ログイン失敗ロック、セッション期限、パスワード再設定、メールアドレス変更 | 方式により工数が大きく変動。SSO・MFAは別途検証が必要 |
| 認可・権限 | ロール数、権限粒度（機能 / データ / 項目単位）、組織階層・部署単位のデータ制限、代理操作、権限の申請・承認フロー | 粒度が細かいほど設計・テスト工数が増加 |
| ユーザー管理 | 登録・招待・退会・休会、一括登録（CSV）、アカウントの棚卸し、退職者の無効化、複数組織への所属 | 管理画面の要否を要確認 |
| 管理画面 | 運用担当者が使う画面の有無（ユーザー管理、マスタ管理、お知らせ、問合せ対応、データ修正） | **見落とすと大きな追加開発になる** |
| マスタ管理 | マスタの種類、更新頻度、誰が更新するか、履歴管理、有効期間、一括取込 | マスタ数に比例して増加 |
| 通知 | メール / プッシュ / SMS / アプリ内通知 / Slack、送信条件、配信停止、送信元ドメイン、テンプレート管理、送信失敗時の扱い | メール配信基盤（SPF/DKIM/DMARC）の設定・外部サービス費用 |
| ファイル | アップロード可能な種類・サイズ上限、ウイルススキャン、プレビュー、保管期間、ダウンロード権限、大容量対応 | ストレージ・転送コストにも影響 |
| 検索・一覧 | 検索条件、並び替え、ページング、あいまい検索 / 全文検索、件数上限、CSV出力 | 全文検索は専用基盤が必要になる場合あり |
| 帳票・出力 | 帳票の種類・レイアウト数、PDF/Excel/CSV、印刷、文字コード（UTF-8/Shift_JIS）、改行コード | **帳票は1枚ごとに工数がかかる**。レイアウトの確定が必要 |
| 入力・取込 | CSV/Excel取込、エラー行の扱い、部分成功の可否、重複判定、文字コード、最大行数 | 取込仕様は例外処理が多く見積が膨らみやすい |
| 履歴・監査 | 操作履歴、変更履歴（誰が・いつ・何を）、削除の方式（論理 / 物理）、復元可否 | データ設計の初期から必要 |
| 承認ワークフロー | 申請・承認・差戻し・代理承認、多段承認、承認ルートの可変性 | 可変にするとワークフローエンジン級の工数 |
| 外部連携 | 連携先、方式（API / ファイル / DB / メッセージ）、頻度、認証、リトライ、仕様の確定状況、テスト環境の有無 | **連携先の都合に依存**。見積前提に明記必須 |
| 決済・課金 | 決済手段、サブスク / 都度課金、返金、請求書、インボイス制度、消費税計算・端数処理 | 法対応・外部サービス審査が必要 |
| 多言語・多通貨 | 対応言語、文言の外部化、文字種、タイムゾーン、通貨、日付・数値表記 | 後付けは高コスト |
| お問い合わせ | 問合せフォーム、チャットボット、FAQ、対応担当者の運用 | 運用体制とセット |
| バッチ・定期処理 | 実行タイミング、処理時間の上限、失敗時の再実行、依存関係、締め処理 | 運用設計と連動 |

### 2.2 画面・UI/UXで確認すべき項目

- [ ] 対応デバイス（PC / スマートフォン / タブレット / 専用端末）、レスポンシブ要否
- [ ] ネイティブアプリの要否（iOS / Android）、ストア公開・審査・アカウントの用意
- [ ] デザインの提供元（クライアント支給 / 自社デザイン / 既存デザインシステム）
- [ ] 画面数・画面の複雑度（一覧 / 登録 / 詳細 / ダッシュボード / グラフ）の概算
- [ ] 画面モックやワイヤーフレームの有無、確定タイミング
- [ ] 画面レビュー・修正の回数（**デザイン修正の回数上限**を決めておく）
- [ ] 既存の操作性を踏襲する必要があるか（現行画面との比較）
- [ ] アクセシビリティの要求水準（[3.7](#37-ユーザビリティアクセシビリティ) 参照）

### 2.3 データ・移行で確認すべき項目

- [ ] 既存データの有無・量・品質（欠損・重複・表記ゆれ・文字コード）
- [ ] 移行対象 / 対象外の範囲（履歴をどこまで持ち込むか）
- [ ] 移行方式（一括 / 段階）、移行リハーサルの回数
- [ ] 旧システムとの並行稼働・切替時の停止許容時間
- [ ] 移行データの突合・検証方法と責任分担
- [ ] 旧システムの仕様書の有無と最新性（なければ解析の工数が必要）

## 3. 非機能要件チェックリスト

非機能要件は**後から変更しにくく、コストに直結する**。「早く・安く・止まらず・安全に」といった曖昧な言葉を、必ず**数値と条件**に置き換える。  
分類は IPA「非機能要求グレード」の大項目（可用性・性能拡張性・運用保守性・移行性・セキュリティ・システム環境エコロジー）を基に、実務で頻出する観点を追加している。

> **ポイント**: 非機能要件は「高いほど良い」ではなく**費用対効果で決める**。要求水準ごとに必要コスト（構成の冗長化・運用体制・テスト工数）が変わることを提示し、合意を取る。

### 3.1 可用性

| 確認項目 | 確認内容・質問例 | よくある値・選択肢 |
| -------- | ---------------- | ------------------ |
| 稼働時間 | サービスを提供する時間帯は？ | 24h365日 / 平日9-18時 / 夜間バッチ帯のみ停止可 |
| 稼働率目標（SLO） | 許容できる停止時間は？ | 下表参照 |
| 計画停止 | メンテナンス停止の可否・時間帯・事前告知 | 月1回・深夜2時間 / 無停止デプロイ |
| 障害時の影響 | 止まった場合の業務・金銭的影響は？ | 影響額 / 代替手段の有無 |
| RTO（目標復旧時間） | 障害からどれくらいで復旧すべきか | 1時間 / 4時間 / 翌営業日 |
| RPO（目標復旧時点） | どの時点のデータまで復旧すべきか | 直前 / 1時間前 / 前日バックアップ |
| 冗長化 | 単一障害点を許容するか | 単一構成 / Multi-AZ / マルチリージョン |
| 障害時の縮退 | 一部機能停止で継続運転してよいか | 参照のみ可 / 全停止 |
| 災害対策（DR） | 大規模災害時の復旧要否・拠点 | 不要 / 別リージョンにバックアップ / ウォームスタンバイ |
| 外部依存の障害 | 外部API・決済・メール等が止まった場合の挙動 | リトライ / キューイング / 手動復旧 |

**稼働率と許容停止時間の目安**

| 稼働率 | 年間の許容停止時間 | 月間の許容停止時間（目安） | 備考 |
| ------ | ------------------ | -------------------------- | ---- |
| 99% | 約3.65日 | 約7.3時間 | 業務時間内のみ・社内ツール向け |
| 99.9% | 約8.76時間 | 約43.8分 | 一般的なWebサービスの目標 |
| 99.95% | 約4.38時間 | 約21.9分 | 冗長化が前提 |
| 99.99% | 約52.6分 | 約4.4分 | 高度な冗長化・運用体制が必要でコスト大 |

> 稼働率の**算出対象**（計画停止を除くか、クラウド基盤の障害を含むか、外部サービスを含むか）を必ず定義する。  
> クラウドサービス自体のSLAを超える稼働率は、単一構成では保証できない。

### 3.2 性能・拡張性

| 確認項目 | 確認内容・質問例 | よくある値・選択肢 |
| -------- | ---------------- | ------------------ |
| ユーザー数 | 登録ユーザー数 / 同時アクセス数 / ピーク時間帯 | 登録1万・同時100 など |
| 処理量 | 1日・ピーク時の取引件数、バッチ処理件数 | 1日100万件 など |
| データ量 | 初期データ量、年間増加量、保存年数 | 年間◯GB・5年保存 |
| 応答時間 | 画面表示・API応答の目標。**測定条件（パーセンタイル・負荷）を併記** | 画面3秒以内 / API P95 1秒以内 |
| バッチ処理時間 | 処理完了すべき時間枠、処理遅延の許容 | 夜間2時間以内 |
| スパイク | キャンペーン・締め日・メール配信直後などの突発負荷 | 平常時の◯倍 |
| 拡張性 | 3年後の想定規模、スケールアウトの要否 | 1年後に3倍 |
| 性能テスト | 負荷試験の実施有無・環境・シナリオ・合格基準 | 実施する場合は別途工数と専用環境が必要 |
| 外部サービス制約 | 外部APIのレート制限、クォータ | 要事前確認 |

### 3.3 運用・保守性

| 確認項目 | 確認内容・質問例 | よくある値・選択肢 |
| -------- | ---------------- | ------------------ |
| 運用体制 | 誰が運用するか（自社 / クライアント / 保守ベンダー / SRE） | 体制未定は最大のリスク |
| 運用時間 | 監視・問合せ対応の時間 | 24h / 平日日中のみ / オンコール |
| 監視 | 監視対象（死活 / リソース / エラー率 / 業務指標）、通知先、通知条件 | [観測性ツール](../../observability/tools.md) 参照 |
| ログ | ログ種別、保存期間、保存先、マスキング | [ログ設計規約](../../guideline/logging/logging-convention.md) 参照 |
| バックアップ | 対象・頻度・世代数・保管場所・復元手順の訓練 | 日次・30世代 |
| リリース方式 | 手動 / CI/CD、リリース頻度、ダウンタイム、ロールバック手順 | |
| 環境構成 | 開発 / 検証 / ステージング / 本番の環境数 | 環境数は費用に直結 |
| 構成管理 | IaC化の要否、設定値・シークレット管理 | |
| 保守契約 | 問合せ窓口、SLA（一次回答時間・復旧目標）、対応時間、対応範囲 | 保守に含む作業 / 含まない作業を明記 |
| 障害対応 | 障害時の連絡フロー、エスカレーション、報告書の要否 | |
| 定期メンテナンス | OS/ミドルウェア/ライブラリの更新、証明書更新、ドメイン更新、棚卸し | **実施者と費用の所在を明確化** |
| ドキュメント | 運用手順書・Runbook・構成図の納品要否 | [運用テンプレート](../../operation/TEMPLATE_OPERATION.md) 参照 |
| サポート期間 | OS・言語・FWのEOL（サポート終了）を踏まえた保守期間 | EOLを超える利用期間なら更新計画が必要 |

### 3.4 移行性

- [ ] 移行対象のデータ・機能・ユーザー（[2.3](#23-データ移行で確認すべき項目) と連動）
- [ ] 移行時期・切替方式（ビッグバン / 段階 / 並行稼働）
- [ ] 切替時の停止許容時間、切戻し（ロールバック）手順の要否
- [ ] 移行リハーサルの回数・環境・本番同等データの利用可否
- [ ] 旧システムの停止・廃止の時期、データ保管義務
- [ ] 利用者への周知・教育・問合せ対応（切替直後の問合せ増加を見込むか）
- [ ] 運用引継ぎ（設計書、手順書、障害対応、ナレッジ）

### 3.5 セキュリティ

| 分類 | 確認項目 |
| ---- | -------- |
| 資産の分類 | 扱う情報の機密区分（個人情報、要配慮個人情報、決済情報、営業秘密）。機密度が構成・運用に影響する |
| 認証・認可 | 認証方式、MFAの要否、パスワードポリシー、権限分離、特権アカウント管理 |
| 通信の保護 | 全通信のTLS化、TLSバージョン、証明書管理、社内通信の暗号化 |
| データ保護 | 保存時暗号化、鍵管理（KMS等）、項目単位の暗号化 / マスキング、DBアクセス制御 |
| アプリケーション脆弱性対策 | OWASP Top 10 の対策、入力検証、CSRF/XSS/SQLi対策、依存ライブラリの脆弱性管理 |
| ネットワーク | WAF、IP制限、VPN / 閉域網、DDoS対策、公開範囲 |
| 秘密情報 | APIキー・トークン・パスワードの保管方法、ローテーション、リポジトリへの混入防止 |
| 監査・ログ | 操作ログ・アクセスログの取得、改ざん防止、保存期間、監査対応 |
| 脆弱性診断 | 診断の要否（ツール診断 / 手動診断）、実施時期、実施者、指摘事項の是正範囲 |
| 外部提出物 | セキュリティチェックシート、ISMS/Pマーク、SOC2等の対応要否 |
| インシデント対応 | 情報漏えい時の連絡体制、通知義務、フォレンジックの要否 |
| サプライチェーン | OSSライセンス、SBOM、外部委託先・外部SaaSの審査 |

- 公開前のWebサービスは [Webサービス公開前ガイドライン](../../guideline/security/public_release_checklist.md) も確認する。
- 脆弱性診断・ペネトレーションテストは**費用が大きく、指摘対応の工数も別途必要**なため、見積から漏れないようにする。

| 環境負荷 | 省電力・リソース最適化の方針（必要な場合） |

## 4. 見積もるべき要件（工数・コストの見落とし防止）

見積は**機能開発の工数だけではない**。以下のカテゴリごとに「含める / 含めない / 別見積」を明示する。  
**含めないものは、見積書の「前提条件・対象外」に必ず記載する。**

### 4.1 工数の抜け漏れチェック

| カテゴリ | 見積に含めるべき項目 | 見落としやすい点 |
| -------- | -------------------- | ---------------- |
| 要件定義・設計 | ヒアリング、要件定義書、基本設計、詳細設計、レビュー、ADR、画面設計、DB設計、API設計 | レビュー指摘対応、**クライアント確認待ちの期間** |
| UI/UXデザイン | ワイヤーフレーム、デザインカンプ、デザインシステム、アイコン・画像、修正回数 | 修正回数の上限が未定だと無限に膨らむ |
| 実装 | 機能実装、共通部品、エラー処理、バリデーション、権限制御、多言語対応 | 例外処理・エラー系・境界値が正常系の同等以上 |
| インフラ構築 | 環境構築（開発 / 検証 / 本番）、IaC、ネットワーク、権限、証明書、ドメイン、WAF | 環境数に比例する。本番と検証の差異調整 |
| CI/CD・開発環境 | パイプライン構築、自動テスト基盤、リリース手順、ブランチ戦略 | 初期構築のみでなく運用・改善も必要 |
| 外部連携 | 連携先との仕様調整、接続テスト、認証設定、エラー・再送処理、連携先テスト環境の調整 | **連携先の遅延は開発側のコントロール外**。待ち時間の扱いを前提に |
| データ移行 | 移行設計、移行ツール開発、データクレンジング、リハーサル、本番移行、突合 | 現行データの品質調査、移行リハーサルを複数回見込む |
| テスト | 単体 / 結合 / 総合 / 受入支援、性能テスト、セキュリティテスト、回帰テスト、不具合修正、テスト仕様書・結果報告 | 不具合修正・再テストの工数、**テストデータ作成**。→ [テスト記録](../../guideline/test/test_record.md) / [負荷試験計画](../../guideline/test/stress_test_plan_template.md) |
| セキュリティ | 脆弱性診断（外部委託費）、指摘対応、セキュリティチェックシート回答 | 診断費用と是正工数が別枠で必要 |
| 実機・端末検証 | OS / ブラウザ / 端末のマトリクス検証、実機調達・レンタル | 対応環境の範囲に比例 |
| ドキュメント | 設計書、API仕様書、運用手順書、操作マニュアル、README、リリースノート | 納品物として約束した範囲すべて |
| 運用準備 | 監視設計・構築、アラート設定、バックアップ設定、Runbook、運用引継ぎ、運用訓練 | **「作って終わり」で漏れやすい** |
| 公開・リリース | 本番リリース、ストア申請（審査対応）、DNS切替、移行当日対応、リリース後ハイパーケア | 夜間・休日作業、リリース後の立会い期間 |
| 教育・展開 | 利用者向け説明会、研修、問合せ窓口の立上げ | 利用者数・拠点数に比例 |
| プロジェクト管理 | 進捗管理、課題管理、定例会、議事録、報告、変更管理、リスク管理 | 開発工数の10〜20%程度は見込む（規模による） |
| 品質保証 | コードレビュー、品質計測、レビュー会 | |
| 調査・検証（PoC） | 技術検証、性能検証、未経験技術の学習・試行 | **不確実性の高い項目は別枠で見積る** |

### 4.2 ランニングコスト・初期費用の見落とし

| 区分 | 項目 | 備考 |
| ---- | ---- | ---- |
| 初期費用 | ライセンス購入、ドメイン取得、SSL証明書、ストアアカウント（Apple Developer / Google Play）、機材・実機、デザイン素材・フォント | 契約主体（誰の名義か）も確認 |
| 月額（インフラ） | クラウド利用料、DB、ストレージ、ネットワーク転送、ログ保管、バックアップ、CDN、WAF | 従量課金の**上限・見込み式**を示す |
| 月額（SaaS・外部API） | メール配信、SMS、プッシュ通知、地図、決済手数料、認証基盤、監視SaaS、AI/LLM API | ユーザー数・リクエスト数での従量課金 |
| 年額 | ドメイン更新、証明書更新、ライセンス更新、ストア年会費 | 更新漏れ事故の予防（担当・期限を明記） |
| 保守・運用 | 保守契約費、監視運用、問合せ対応、軽微改修枠、定期メンテナンス | 「保守に含む / 含まない」を具体例で明記 |
| 人件費（運用） | 運用担当の人数・稼働、オンコール手当 | 自社開発で特に忘れやすい |
| 更新・延命 | OS/言語/FWのEOL対応、ライブラリのメジャーアップデート | 数年後の追加費用として計画 |
| 出口（終了時） | データエクスポート、解約手続き、データ消去証明 | 契約終了時の費用 |

### 4.3 見積の前提条件（必ず明記する）

見積書には、以下を**前提条件**として書き、前提が崩れた場合は再見積となることを合意する。

- [ ] 対象範囲（機能・画面数・帳票数・API数・連携先の数など、**数量ベース**）
- [ ] 対象外の範囲（明示的に含まないもの）
- [ ] 対応環境の範囲（OS / ブラウザ / 端末）
- [ ] 非機能要件の水準（稼働率、性能、セキュリティ診断の有無）
- [ ] クライアント側の作業・提供物とその期限（仕様確定、データ提供、環境提供、確認回答）
- [ ] 外部サービスの仕様確定状況・テスト環境の提供
- [ ] レビュー・修正の回数、受入テスト期間、検収条件
- [ ] 要件変更時の扱い（変更管理プロセス、追加見積）
- [ ] 見積の有効期限、為替・原価変動の扱い（外部サービスを含む場合）
- [ ] 開発体制・稼働前提（人数、稼働率、期間）
- [ ] 見積の確度（概算 ±◯% / 確定）と、確度を高めるための追加確認事項

### 4.4 見積の確度を上げるための手法

| 手法 | 内容 |
| ---- | ---- |
| 数量ベース見積 | 画面数・帳票数・API数・テーブル数・バッチ数を数え、種別（単純 / 標準 / 複雑）ごとの単価で積み上げる |
| 類似案件比較 | 過去の類似案件の実績（見積 vs 実績）と比較し、乖離要因を確認する |
| 三点見積 | 楽観 / 最頻 / 悲観の3値を出し、（O + 4M + P）÷ 6 で期待値、(P − O) ÷ 6 でばらつきを把握する |
| リスクバッファ | 不確実性（未決事項、外部依存、新規技術）に応じて別枠で予備を持つ。**根拠なしの一律上乗せは避け、理由を説明できる形にする** |
| 段階的見積 | 要件が不確実な場合は、要件定義・設計フェーズを先行して見積り、開発フェーズは確度が上がった後に再見積する |
| PoC先行 | 技術的に不確実な項目は、PoC（技術検証）を先に実施して見積の精度を上げる |
| 準委任での開始 | 要件が固まっていない場合、請負で固定せず準委任（期間・体制ベース）で開始する選択肢を提案する |

### 4.5 見積で「別途協議・別見積」にしやすい項目

以下は金額・工数が読みにくく、**契約後にトラブルになりやすい**ため、最初から別枠として明示する。

- 仕様未確定の外部連携・外部システム改修への追従
- データ移行（現行データの品質が不明な場合）
- 性能チューニング・負荷対策（要件が数値化されていない場合）
- 脆弱性診断の費用・診断指摘の是正
- 大規模なデザイン修正・仕様変更
- 運用開始後の保守・障害対応・問合せ対応
- 対応OS・ブラウザの追加、新OSバージョンへの追従
- 法改正・外部サービス仕様変更への対応

## 5. ヒアリングの技法と曖昧要件の検出

### 5.1 曖昧な言葉を定量化する

要件に以下の言葉が出たら、**具体的な数値・条件・例**に置き換える。

| 曖昧な表現 | 確認する質問 | 具体化の例 |
| ---------- | ------------ | ---------- |
| 高速に / サクサク | 何秒以内？ どの操作？ 何人同時？ | 一覧表示は100ユーザー同時利用で P95 2秒以内 |
| 止まらない / 高可用 | 何時間の停止まで許容？ 何を止めたくない？ | 月間稼働率99.9%（計画停止を除く） |
| セキュア / 安全に | 何から何を守る？ 準拠基準は？ | 個人情報を保存時暗号化。OWASP Top 10 対策、診断1回 |
| 使いやすい | 誰が、どんな状況で使う？ 評価基準は？ | 初見の利用者が説明なしで主要操作を5分で完了 |
| 柔軟に / 拡張可能に | どの変更を想定？ 頻度は？ | 通知種別の追加を設定のみで可能 |
| 大量のデータ | 何件？ 増加ペースは？ 保持年数は？ | 初期500万件、年間200万件増、7年保存 |
| 最新のブラウザ / 主要端末 | 具体的な名称・バージョンは？ | Chrome / Edge / Safari の最新2バージョン |
| 既存と同じように | 現行のどこまで同じ？ 差異は？ | 現行画面◯◯と同一項目。ただし▲▲は変更 |
| 適宜 / 随時 / 必要に応じて | 条件・頻度・実施者は？ | 毎月末営業日に自動実行 |
| 将来的には | いつ頃？ 今回は含む？ 対象外？ | 第2フェーズで対応。今回は拡張可能な設計までとする |
| 一般的な / 普通の | 何を基準にした一般的？ | 具体例（サービス名・画面）で合意する |
| できるだけ / なるべく | 譲れない水準は？ 優先度は？ | Should（努力目標）として扱い、未達でも検収可とする |

### 5.2 要件の書き方（テスト可能な形式にする）

要件は以下を満たす形で記述する。

- [ ] **誰が**（アクター・ロール）
- [ ] **何を**（対象・操作）
- [ ] **どの条件で**（前提・トリガー・負荷条件）
- [ ] **どの水準で**（数値・基準）
- [ ] **どう確認するか**（テスト方法・受入条件）
- [ ] **優先度**（Must / Should / Could / Won't）
- [ ] **根拠**（なぜその水準が必要か）

**記述例**

```text
悪い例：システムは高速であること。
良い例：管理者ロールが注文一覧（最大1万件）を検索したとき、同時接続50ユーザーの条件下で
        95%のリクエストが2秒以内に応答すること。計測は検証環境の負荷試験で実施する。（Must）
```

### 5.3 ヒアリングのコツ

- 「現状の業務フロー」と「困りごと」から聞き、**解決策の押し付けではなく課題から要件に落とす**。
- 要望（Want）の裏にある**目的（Why）** を確認する。手段が目的化していることが多い。
- 例外ケース（キャンセル・取消・訂正・差戻し・期限切れ・重複・同時操作）を必ず確認する。
- 「誰が運用するのか」「誰が問合せに答えるのか」「誰が費用を払うのか」を確認する。
- 口頭での合意は**必ず議事録に残し、相手に確認してもらう**。
- 「今回はやらないこと」を意識的に合意する（スコープの境界を明確にする）。
- 確認に対する回答が得られない場合、**仮置きの値を提示して異議がなければ確定**とする運用が有効。

### 5.4 レッドフラグ（リスクの兆候）

以下が見られたら、見積にバッファを持つ、フェーズを分ける、追加確認を行う等の対策を取る。

| 兆候 | 想定されるリスク | 対策 |
| ---- | ---------------- | ---- |
| 決裁者に会えない | 後から要件がひっくり返る | 決裁者レビューの機会をマイルストーンに組み込む |
| 要件が「◯◯のように」で終わる | 範囲が無限に広がる | 具体的な画面・機能単位に分解する |
| 既存システムの仕様書がない | 解析・移行工数の膨張 | 現行調査フェーズを先行して見積る |
| 連携先の仕様が未確定 | 手戻り・遅延 | 前提条件に明記し、仕様確定を期限付きで依頼 |
| 非機能要件の話が出ない | 後から高い水準を求められる | こちらから[第3章](#3-非機能要件チェックリスト)を使って確認・合意する |
| 納期が先に決まっている | 品質・範囲を犠牲にする圧力 | 優先順位付けでスコープを調整する |
| 予算が先に決まっている | 機能が予算を超える | Must / Should を整理し、段階リリースにする |
| 担当者が多忙・回答が遅い | レビュー待ちで遅延 | 回答期限とエスカレーションルールを事前合意 |
| 「簡単にできるはず」 | 工数の過小評価 | 難しさの根拠（例外・連携・データ）を可視化する |
| 運用担当が決まっていない | リリース後の運用崩壊 | 運用体制・引継ぎを要件に含める |

## 7. クイックチェック（最低限これだけは確認する）

時間がない場合でも、以下の項目は**必ず**確認する。

- [ ] 目的・成功指標・対象外が明確である
- [ ] 最終決裁者と、要件確認の回答期限が決まっている
- [ ] 対応環境（OS / ブラウザ / 端末）の範囲が決まっている
- [ ] ユーザー数・データ量・ピーク負荷の想定がある
- [ ] 稼働時間・許容停止時間・RTO / RPO の合意がある
- [ ] 認証・権限・個人情報の扱いが決まっている
- [ ] 外部連携先の仕様と費用負担者が決まっている
- [ ] 運用体制（誰が監視・保守・問合せ対応を担うか）が決まっている
- [ ] ランニングコスト（インフラ・外部サービス・保守）の見積がある
- [ ] テスト範囲（性能・セキュリティ診断・実機検証）が決まっている
- [ ] 移行対象データと移行方式が決まっている（既存システムがある場合）
- [ ] 見積の前提条件・対象外・変更時のルールが明記されている
- [ ] 未決事項が一覧化され、担当と期限が設定されている
