## 1. 文書の目的

### 1.1 この文書で決めること

本書では、以下を明確にする。

1. プロジェクトを開始する背景と解決すべき課題
2. 対象となる利用者・関係者
3. 利用者・事業・組織が求める価値
4. 実現したい状態と成功指標
5. 対象範囲と対象外
6. 優先順位、制約、前提、リスク
7. 要件定義へ引き継ぐ要求事項

### 1.2 この文書で決めないこと

以下は、要求定義では原則として確定しない。

- 画面レイアウト、画面遷移、入力項目
- API、DB、ファイル、バッチの詳細仕様
- システム構成、クラウド、フレームワーク、ライブラリ
- クラス設計、テーブル設計、実装方式
- 詳細なテスト項目

ただし、法令、契約、既存環境などにより実現方式が事実上固定される場合は、制約として記載する。

### 1.3 要求定義と要件定義の違い

| 観点 | 要求定義 | 要件定義 |
| ---- | -------- | -------- |
| 目的 | 価値・目的・課題の明確化 | 機能・仕様・実現条件の具体化 |
| 主な問い | なぜ作るのか、誰のためか | 何を、どのように実現するか |
| 中心視点 | 利用者、事業、業務 | システム、機能、開発 |
| 主な成果物 | ペルソナ、課題、価値、成功指標、構想シナリオ | 機能一覧、画面仕様、非機能要件、受け入れ条件 |

## 20. このテンプレートの使い方

1. 最初に「課題」「対象利用者」「目的」「成功指標」「スコープ外」を埋める
2. 要求は、機能名ではなく「誰が、何を達成したいか」で記述する
3. 要求には、背景・根拠・要求元・優先度を付ける
4. 根拠が弱いものは断定せず、仮説として検証計画に回す
5. 画面・API・DB・技術選定の議論が始まったら、要求と実現手段を分離する
6. 利害が衝突する要求は、曖昧なまま残さず意思決定記録に残す
7. 成功指標は、開発完了ではなく利用者・業務・事業の変化で定義する
8. 要求定義の完了後、本書の要求IDを要件定義書の機能・非機能・受け入れ条件へ紐づける

### 最重要チェック

- 「作ること」自体が目的になっていないか
- 本当に解決すべき課題か、それとも手段への思い込みか
- 声の大きい関係者の希望だけを要求にしていないか
- 成功を客観的に判定できるか
- やらないことが明確か
- 技術的に面白い案へ早すぎる段階で寄っていないか
